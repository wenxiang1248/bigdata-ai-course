大模型的上下文

每一轮请求，模型"看得见的全部输入"——决定了它这一次表现得像不像个聪明人。

类比
一段会被塞进模型的剧本
本质
一个滑动窗口里塞好的 token 序列
四类消息
system · user · assistant · tool
关键限制
窗口大小 + Lost in the Middle
核心做法
Context Engineering

1 ·学习目标

  • 能 说出 什么是大模型的"上下文"，并把它和"提示词"区分开。
  • 能 画出来 一次请求里上下文是如何被组装出来的。
  • 能 解释"Lost in the Middle"现象为什么不能忽视。
  • 能 应用 至少 3 种 Context Engineering 的常见手法。
  • 能 避开 把"上下文"误用成"长期记忆"的常见坑。

2 ·核心问题

  1. "上下文"和"提示词"到底是不是一个东西？
  2. 一次 LLM 请求里，模型实际看到的是哪些 token？
  3. 为什么"context window"不能无限大？
  4. 为什么把全部历史塞进去，模型反而表现变差？
  5. 想让 Agent 在长任务里不丢信息，"上下文工程"到底在做什么？

3 ·结构化解释

3.1 · 心智模型：一段被装订好的剧本

把"上下文"想成演员上台前拿到的那份剧本：

  • 剧本只装订当时的情况——它不写"上次发生了什么"，除非有人把它写进页。
  • 剧本每一页都要钱——总字数（token）一旦超量，模型要么截断、要么压缩。
  • 剧本前后会被看得最清楚，中间容易糊——这一点是很多灵异 bug 的来源。

3.2 · 组成解剖

一份上下文通常由 4 类角色组成：

角色用途谁写稳定性
system给模型"我是谁、我要遵守什么规则"开发者几乎不变
user当前轮的用户问题用户每轮变
assistant历史轮模型自己说过的话模型每轮追加
tool工具调用返回值（如搜索结果）外部系统按需插入

system 不是 prompt。很多产品把 system 和 user 混在一起描述，实际会让模型很困惑。System 是"身份+规则+输出格式"，user 是"这一次要问什么"。

3.3 · 运作机制（按步骤展开）

  1. 收集：把 system、固定指令、用户输入、历史摘要、检索片段、工具结果排好序。
  2. Tokenize：所有内容被切成一个 token 序列（常见词一个 token，汉字一般 1~2 字一个 token）。
  3. 截断或压缩：若超过窗口，常见策略是"保留 system + 最近 N 轮 + 压缩中间"。
  4. 送进模型：模型一次性看到这段序列，自回归地输出新 token。
  5. 回写：本轮的输出会被回写到历史，作为下一轮 assistant 消息的一部分。

3.4 · 为什么这件事重要

因为决定 LLM 表现的，从来不是"参数量大不大"，而是"这一轮的上下文选得好不好"。同样一个 GPT，把"商品退货政策"塞到 system 里、再加上一句"顾客原话如下"，回答质量就完全不一样。Context Engineering（上下文工程）就是把这套手艺抽出来：当窗口有限、历史很长、知识会变的时候，设计一个能稳定拼出好上下文的流程。

3.5 · 代码级一瞥（构造一次"最小合规"的上下文）

messages = [
    {"role": "system",
     "content": "你是电商客服助理。退货政策：7 天内可退、'
                '生鲜除外。每轮只能调用一个工具。"},
    {"role": "user",
     "content": "我 5 天前买的芒果烂了，能退吗？"},
    # —— 历史对话被压成一条摘要塞进去，不放原文 ——
    {"role": "assistant", "content": "[摘要] 用户曾因物流延迟抱怨一次。"},
    # —— 工具调用结果也属于上下文 ——
    {"role": "tool", "tool_call_id": "t1",
     "content": '{"订单号": "A8821", "商品": "芒果 1kg", '
                 '"下单时间": "5 天前 10:24"}'},
]

这一段里你能看到三件事：

  • system 写身份和规则，短而稳定。
  • 历史对话被"摘要"而不是原文，留给新内容的空间才大。
  • 工具的原始返回是 JSON，模型读得懂，但占字数。

4 ·应用案例：给一个电商客服 Agent 装 Context

场景：你做了个电商客服 Agent，每天要回答上千名顾客。其中不少问题需要看"订单状态"或"产品手册"才能答。纯拼一个超长 prompt，模型回答了一半开始胡说。

你要做的，是给这个 Agent 设计一个"上下文拼装线"：

  1. 入口：用户进来一句话——"我买的芒果烂了"。
  2. 工具调用：Agent 调 order_query(user_id)，查到 5 天前下单的 A8821。
  3. 检索：把"芒果 烂了 退货"丢去知识库检索，命中了一段"水果类售后 3 条"——这是 RAG。
  4. 上下文拼装：
    1. system：你定义的身份与"只在有权资料下作答"的规则。
    2. tools：订单详情 + RAG 片段。
    3. user：原话。
    4. 短期摘要：用户最近 3 条对话的摘要。
  5. 生成：模型基于这一组合上下文，给出"可以退，我已发起退款，预计 1~3 个工作日"。
  6. 落库：把这一轮的对话、订单、退款指令写回数据库，供下次复用。

结果：原本"十分钟糊一句"的 Agent，现在能在一个 8K 的小窗口里精确回答，因为它每一轮只看见应该看见的那些东西。

5 ·概念辨析

5.1 · Context vs Prompt vs Memory

维度Context（上下文）Prompt（提示词）Memory（记忆）
范围这一次模型看见的全部你写给模型的那一句话或一段话跨会话、跨请求持久化的信息
时间单次请求单次请求长期
谁来写系统（apps/orchestrator）人或开发者模型与系统共同沉淀
可被裁剪是（摘要、检索、截断）是（重写、压缩）需要专门存储

5.2 · 常见误区

  • "把上下文当成数据库" — 上下文是一次性场景，不是存东西的地方；想跨会话记住，请用 Memory。
  • "上下文越长越好" — 研究（Lost in the Middle, 2023）显示，模型在长上下文中段最容易丢信息，关键内容要放开头或结尾。
  • "system 就是 prompt" — System 写身份和规则；user 写问题；混在一起会让模型"不知道该听谁的"。
  • "简单任务也要重设计" — Context Engineering 不等于"塞满"，对"把这句话翻译成法语"反而有害。

6 ·自测问题

Q1 · "上下文"和"提示词"是一回事吗？ 不是。提示词是你写的输入；上下文是这一次请求中模型实际看到的所有 token 序列，包含多类角色消息、工具结果、检索片段。前者是一个工件，后者是一个时刻。
Q2 · 一个 200K 窗口的模型，是不是就能"记住"超长文档？ 能"装下"，但不一定能"读好"。模型在长上下文的中段最容易漏（Lost in the Middle）。工程上仍要把关键信息放在头部或尾部。
Q3 · 为什么要把 system 和 user 分开？ System 写稳定的身份、约束、输出格式；user 写当前问题。混在一起会让模型在每轮重新猜"我到底是谁"，稳定性下降。
Q4 · 当历史对话超出窗口时，常见的三种处理是什么？ ① 截断（保留最近 N 轮）；② 摘要（让模型把中段压成 1~2 条笔记）；③ 检索（用 RAG 在历史里找最相关几条）。
Q5 · 一份 prompt 写得很长很完整，效果就一定更好吗？ 不一定。超长 prompt 会稀释每条指令的权重，并触发 Lost in the Middle。设计良好的上下文往往短、清晰、目标明确。
Q6 · Context Engineering 和 Prompt Engineering 到底是什么关系？ Prompt Engineering 是 Context Engineering 的一部分（写作提示词的那一段）；Context Engineering 还包括选择 RAG 切片、写 system、设计摘要策略、管理 tool 返回——是把"喂什么给模型"这件事整体上做对。
