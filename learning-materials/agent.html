Agent（智能体）

一个能"看着目标、自己选工具、自己判断下一步"的 AI 程序。

类比
有目标的实习生，不是聊天机器人
本质
在循环里持续决定「下一步做什么」
关键组件
LLM · 记忆 · 工具 · 反馈
核心能力
规划 + 调用 + 反思
典型风险
死循环 · 幻觉工具调用

3 ·结构化解释

3.1 · 心智模型：带目标的循环

先抛开术语，把 Agent 想成「一位被指派了任务的实习生」：

  • 目标明确（"帮我在 200 字内总结这篇文章的三点争议"）。
  • 可调用的工具明确（搜索引擎、计算器、读 PDF、跑 SQL）。
  • 执行过程是一个个"看一眼情况、决定一步、做一步、再看一眼"的循环。
  • 退出条件明确：要么时间到了，要么结果判定为"够了"。

  • Plan-and-Execute 就是把"思考"拆成"先规划，再逐步执行"。
  • ReWOO 就是让"思考"在跑工具之前先把所有计划生成出来。

3.3 · 运作机制（按步骤展开）

  1. 接受目标：用户给一个高层目标，不给步骤。
  2. 初始化上下文：把目标、可用工具描述、历史摘要塞进 prompt。
  3. 进循环：把当前上下文喂给 LLM，让它输出"下一步是调用哪个工具+参数"。
  4. 执行工具：调外部系统，把结果塞回上下文。
  5. 判断是否收尾：若 LLM 输出"我得出最终答案了"或达到轮次上限，就结束。
  6. 输出 & 留痕：把答案返回用户，把整段轨迹写进记忆供下次复用。

3.4 · 为什么这件事重要

因为 LLM 本身只能"读一段、写一段"。一旦任务需要"打开网页看一眼、改一行数据库、再看一眼"，单次对话就退化成猜测。Agent 模式让 LLM 第一次有了"自己发现信息、自己验证自己、自己迭代答案"的资格——这是它从"问答工具"走向"工作伙伴"的临界点。

3.5 · 代码级一瞥（最小可运行的 ReAct 风格循环）

"""最小 Agent 循环：观察→思考→行动→观察，直到模型说 DONE。"""
from openai import OpenAI

client = OpenAI()

TOOLS = {
    "get_time":      "返回当前时间（占位）。",
    "search_docs":   "在公司文档库里搜索一段文字，返回前 3 条摘要。",
    "calc":          "计算一个数学表达式并返回数值。",
}

def call_tool(name, args):
    # 真实实现里这里应该按 name 路由到具体函数
    if name == "calc":
        return str(eval(args["expr"]))
    return f"[{name} 收到: {args}]"

history = [{"role": "system", "content":
    f"你是实习生。你可以调用工具：{TOOLS}。"
    "想停就回复 DONE: <结论>。"}]

user_goal = "明天下午 3 点提醒我开会。"
history.append({"role": "user", "content": user_goal})

for step in range(8):                            # 终止条件：最多 8 轮
    msg = client.chat.completions.create(
        model="gpt-4o-mini", messages=history
    ).choices[0].message

    if msg.content.startswith("DONE:"):
        print("最终答案:", msg.content[5:])
        break

    # 模型决定调用哪个工具 + 哪些参数
    tool, args = msg.tool_call["name"], msg.tool_call["args"]
    result = call_tool(tool, args)

    history.append({"role": "assistant", "content": msg.content})
    history.append({"role": "tool", "content": result})

4 ·应用案例：让 Agent 自动整理一周的销售数据

场景：你是一名运营，每天早上 9 点前需要把"上周各渠道销售额 Top 10、退款异常订单、需要关注的客诉"汇成一份 1 页简报。

输入（用户的唯一一句话）：

"读一下 sales_db 里上周的数据，做一份今天早上 9 点要看的简报。"

Agent 走过的决策点：

  1. 观察：当前时间是周一的 8:55；目标里有一个固定产出模板。
  2. 思考 + 工具：调 sql_query，拉出上周的 orders 与 refunds 表；调 ticket_query 拉出带"投诉"标签的会话。
  3. 思考 + 工具：调 python_runner，按渠道聚合销售额并排序；调 anomaly_detect 找出金额异常的退款。
  4. 观察：模板要求一段开场一段数据；当前上下文已备齐所有数据。
  5. 收尾：把数据写入 report_{date}.md 并调用 send_email 发给你。

结果：你 9 点打开邮箱，就看到一份带 Top 10 渠道、退款异常明细、待处理客诉链接的简报，并且 Agent 把每一次 SQL 留到了 audit.log 里供你回头核对。

这个场景展示了 Agent 的三件事：把目标翻译成步骤、用工具补足 LLM 没有的能力、每次产出都留痕。

5 ·概念辨析

5.1 · Agent vs Workflow vs RAG

维度Agent（智能体）Workflow（工作流）RAG（检索增强）
路径选择由 LLM 在运行时动态决定由人在写代码时静态编排固定走检索→生成
工具调用多次、按需通常是 0 或 1 次通常 0 次
适合任务开放、需要探索流程固定基于已有知识的问题
不确定性高低中

一句话总结：RAG 给 Agent 补"知识"，Workflow 给 Agent 补"纪律"，Agent 给 Workflow 补"应变"。

5.2 · 常见误区

  • "工具越多越好" — 工具多了 LLM 选择困难，回归测试做不完。给 Agent 恰好够用 的工具就好。
  • "Agent 能自动纠错" — 没有任何评估与回放机制的 Agent 不会自我改正；它会一错再错同样风格。
  • "Agent 适合做一切" — 凡是能 3 步列清楚的任务，用 Workflow 更稳；Agent 是为"流程不完全确定"的任务准备的。
  • "上下文越长越好" — 见 learning-materials/llm-context.html 的 Lost-in-the-middle 现象。

6 ·自测问题

Q1 · Agent 跟一次性 LLM 问答的本质区别是什么？ 一次性问答是"输入→输出"；Agent 是"输入→循环判断→多次行动→输出"，多了目标、循环、工具、终止条件四件事。
Q2 · ReAct 名字里的"Re"和"Act"分别指什么？ Re = Reason（推理，先想清楚），Act = Act（行动，再调工具）；二者交替执行。
Q3 · 一个 Agent 任务最常见的两个"跑飞"原因是什么？ ① 没有硬上限：Agent 一直循环烧光预算；② 没有评估：它不知道自己错了，继续错。
Q4 · 为什么不直接用更大的 prompt 把所有工具都告诉 LLM？ 提示越长模型越会"丢失中间"信息（Lost in the Middle），且工具越多选错概率越高。需要在 Agent 里按需暴露工具，而不是一次性把工具谱全塞进去。
Q5 · Agent 在课程作业里什么时候比脚本更划算？ 当任务"步骤不确定但目标明确"时——比如"调研并对比三种开源数据库框架"适合 Agent；"把 CSV 里某列求和"用脚本。
Q6 · 看到 Agent 输出"我决定调用 tool X"但实际上 X 不存在时，问题通常出在哪？ 通常是工具描述不清或工具注册位置和 docstring 不一致。Agent 是按"名字+描述"来选工具的，描述错了，等于菜单写错了。
