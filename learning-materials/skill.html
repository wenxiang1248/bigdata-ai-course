Skill（技能）

一组结构化的、可复用的指令包，让 Agent 在某个具体任务上表现得更稳、更专业。

类比
餐厅的"标准作业流程"——保证每个厨师都能稳定出同一道菜
本质
一份带 frontmatter 的 Markdown 指令包
关键收益
省心 / 稳定 / 可分享
最易混淆
≠ 一次性 prompt

TL;DR

  • Skill 是 Markdown 文件，前后两个 --- 之间是元数据，下面是说明。
  • 它是 "什么时候用" + "怎么做" + "做完检查什么" 的合集。
  • 它把"同一个流程在每次对话里都要重新解释一遍"省掉。

为什么这件事重要

大型语言模型的强项是"即兴"，弱项是"稳定地重复"。Skill 就是把"你会做的事"变成 Agent 能稳定执行的能力。今天上班写的 Skill，明天、下次、新电脑上都能直接复用——它把"你和 Agent 的默契"沉淀成了可携带的文字。

1 · 心智模型

2 · 解剖：一个好的 Skill 长什么样

  • frontmatter（顶部的元数据）：name（唯一标识）+ description（写明何时使用）。后者尤其关键——是触发匹配的主要依据。
  • when to use：用人话写出"用户讲哪类话时该启动我"。越具体越好，避免与其它 Skill 撞车。
  • inputs / outputs：标清楚 Skill 需要什么输入、产出什么输出。表格化最清楚。
  • workflow：分步操作清单。这是 Skill 的"主菜"。
  • quality checklist：完工前要确认的几条事——决定该 Skill 的可复用性。
  • examples / failure modes：正反样本，防止下次跑偏。

3 · 运作机制

  1. 写：用 Markdown，按上述骨架写一个 SKILL.md。
  2. 放：项目级放 ./.workbuddy/skills/<name>/SKILL.md；个人级放全局 skills 目录。
  3. 匹配：每次会话开始时，Agent 读所有可用 Skill 的 description。
  4. 触发：用户的话与某个 Skill 的 description 命中 → 把该 Skill 的全文加载进上下文。
  5. 执行：Agent 按 Skill 的 workflow 工作，并按 checklist 自检。

4 · 一个具体的应用场景

场景：把"每周周报"沉淀成一个 Skill。

你发现自己和 Agent 在过去两个月里，每周都要重复同一段对话：

  1. "读一下 notes/week-N.md。"
  2. "按三段整理：做了什么、学到什么、下周计划。"
  3. "不要写客套话。"
  4. "不超过 400 字。"

每次都要重新敲一遍。这就是写 Skill 的最强信号——你重复做同一套多步骤流程。你把这个流程写成 .workbuddy/skills/weekly-report/SKILL.md，从此以后只要说一句"做周报"，Agent 会自动：

  • 匹配 description（"周五下午 / 用户说做周报"）→ 把 Skill 全文加载进 Context。
  • 读你指定的笔记。
  • 按三段排版。
  • 按 checklist 自检（≤ 400 字、无客套话、时间表述统一）。

写一次，用 N 次；换电脑、换助理，也能复用。这就是 Skill 的价值。

常见误区

  • "Skill 就是写 prompt"。错。prompt 是 Skill 的一部分；Skill 是带 frontmatter、有触发逻辑、有 checklist 的完整包。
  • "越多 Skill 越好"。错。每个 Skill 都会占上下文，写多了反而稀释主任务的可读性。
  • "description 写不写都行"。错。description 决定"何时触发你"，写得模糊就等于让 Skill 永远不被使用。
  • "Skill 能让模型变聪明"。不能。Skill 让模型"更稳"——同一道题反复做得到同样的好，但不能做它原本做不了的题。

6 · 代码级一瞥（一个最小可用的 Skill）

---
name: weekly-report
description: 生成本周工作总结的 Markdown。每周五下午、或用户说"周报"时使用。
---

# Weekly Report Generator

## When to use
用户说"做周报"、"总结本周"、"weekly report"。

## Inputs
- 本周项目笔记（notes/week-N.md）
- 用户的角色 / 团队（可选）

## Workflow
1. 读取 notes/week-N.md。
2. 按"做了什么 / 学到什么 / 下周计划"三段组织。
3. 输出 Markdown，不要超过 400 字。

## Quality checklist
- [ ] 三段齐全，顺序固定。
- [ ] 没有"当然可以"或"希望对您有帮助"这类客套话。
- [ ] 时间表述统一（不混用"昨天/周一/9 月 1 日"）。

这就是一个 Skill 的最小完整样例。任何比这"更复杂但仍然是这八股"的 Skill，都站得住脚。

7 · Recap & 自检

1. Skill 是什么物理形式？一个放在 .workbuddy/skills/<name>/SKILL.md 的 Markdown 文件，前后 --- 之间是 frontmatter，下面是正文。
2. 决定 Skill 被触发的关键是什么？frontmatter 里的 description。它写明"用户讲哪类话时该用我"，写得越具体、越不撞车越好。
3. 什么时候该考虑写一个 Skill？当你发现自己或 Agent 反复被同一个多步骤任务"卡住"，且每次都要在对话里重新解释一遍流程时。
4. Skill 和 prompt 有什么区别？prompt 是一次性的指令；Skill 是带触发条件、有 workflow 与 checklist 的可复用程序包，写一次、跑多次。
5. 为什么不"什么 Skill 都写"？Skill 占上下文位置，过多会稀释模型注意力。一般每项目 5–15 个 Skill 是健康规模。
6. 项目级 Skill 和用户级 Skill 各适合什么场景？项目级 Skill 适合"只有这个项目需要"的流程（如打包作业提交）；用户级 Skill 适合"走到哪都管用"的个人偏好（如沟通语气、汇报模板）。
